# B-21 UI詳細仕様

Status: Draft / partially accepted
Decision ID: B-21

## 1. Home画面の基本レイアウト

ホームは「今日、マネージャーが見るべき判断材料」を最短で把握できる構成にする。

### 1.1 上段: 4枚のサマリーカード

PCでは横並び4列を基本とする。

現時点のイメージ:

1. 今日の異常
2. 今日の要確認
3. 今日の委譲候補
4. 今日の褒める候補

重要:
- 上記4項目の名称・最終カテゴリは未確定。
- ただし「今日の重要な判断材料を、少数のカードとして横並びで即時把握する」というレイアウト原則は採用する。
- 各カードは件数だけではなく、その日の重要シグナルへの入口として機能する。
- KPI達成率だけをトップに置くダッシュボードにはしない。

### 1.2 下段: 3つの情報ブロック

PCでは横並び3列を基本とする。

現時点のイメージ:

1. 確認事項リスト
2. 今日のスケジュール
3. チーム状態

重要:
- 項目名・表示詳細は未確定。
- 「サマリーカードの次に、今日の行動・時間・チーム状況を3ブロックで確認する」という情報階層は採用する。

## 2. 共通Interaction Pattern

COMESでは画面遷移を最小化し、一覧・俯瞰の文脈を維持したまま詳細確認・一次編集を行う。

### 2.1 Centered Modal

Home、Team、Decision Packの詳細表示は、PCでは共通して中央の大きめModal Dialogを基本とする。

採用する見え方:
- 画面中央に幅広のモーダルを表示
- 元画面は背面に残す
- 背景には半透明の暗いoverlayをかける
- 右側Drawerを標準パターンにはしない
- 閉じると元の一覧・俯瞰位置へ戻る

目的:
- 現在地を失わない
- 画面遷移を減らす
- 「見る → 判断する → 軽い処理をする」を短い操作で完結させる

### 2.2 詳細画面へ遷移する境界

情報量が多く、履歴や長期推移まで見る必要がある場合のみ専用画面へ遷移する。

例:
- KPI詳細推移
- 1on1履歴
- Bottleneck詳細
- 長期人物履歴

原則:

```text
Overview / List
  ↓
Centered Modal
  ↓
確認 + 一次編集
  ↓ 必要な場合のみ
Detail Page
```

## 3. タスク画面

タスク画面は「今日やること」を最優先にし、時間軸で整理する。

### 3.1 基本3分類

1. 今日やること
2. 1週間以内にやること
3. 急ぎじゃない

優先順:

```text
今日やること
↓
1週間以内にやること
↓
急ぎじゃない
```

### 3.2 PCレイアウト

PCでは3つの時間軸を横並びのボードとして表示する。

左から:

1. 今日やること
2. 1週間以内にやること
3. 急ぎじゃない

各列にはタスクカードを縦に並べる。

タスクカードの基本情報:
- タスク名
- 簡潔な説明
- 担当者 / 関係者
- 期限
- 優先度
- 必要に応じたコメント・関連情報
- 補助シグナル

「今日やること」は背景・見出しなどで他列より視覚的に強くする。

### 3.3 マネジメント判断シグナル

各タスクには必要に応じて補助シグナルを付与する。

例:
- 期限切れ
- 停滞
- 委譲候補
- 仕組み化候補
- 要レビュー
- 高リスク / 要確認

重要:
- シグナルはタスクの所属レーンではない。
- 「通常」というラベルは持たない。
- 停滞は「本来進むはずのタスクが一定期間更新されていない / 待ち理由により止まっている」状態を示す。

原則:

```text
When = 今日 / 1週間以内 / 急ぎじゃない
How = 自分でやる / 任せる / レビュー / 仕組み化
```

### 3.4 AI提案からのタスク化

AI提案を人間が「採用」した場合、確認モーダルを挟まず即時にタスクへ反映する。

反映対象:
- title
- description
- assignee
- related_person
- due_bucket
- due_date
- priority
- recommended_action
- expected_outcome
- success_criteria
- estimated_minutes（存在する場合）
- source_refs

採用後に変更したい場合は、生成されたタスク自体を編集する。

### 3.5 AI提案と人間メモの分離

タスク詳細では、AI由来情報と人間追記を明確に分離する。

AI提案ブロック:
- 何をするか
- なぜやるか
- 推奨アクション
- 対象者
- 期限
- 優先度
- 根拠
- expected outcome
- success criteria

人間メモブロック:
- 自由記載メモ
- 実行時の補足
- 伝え方の注意
- タイミング調整
- 実施後メモ

実施後メモは任意とする。

### 3.6 今日のモード

AI返却JSONの `management_focus_type` / `management_focus_summary` を、タスク画面上部に表示する。

例:

```text
今日のモード: フォロー優先
停滞案件の解消とメンバーフォローを優先。新規営業は最低限にする。
```

モードはAI提案として表示し、手動変更は行わない。

### 3.7 稼働時間と実行可能性

タスク画面上部に以下を表示する。

- 稼働可能時間
- 今日タスク見積合計
- 残り余力
- 超過時間

ルール:
- 通常稼働時間の初期値は8時間。
- 通常稼働時間は設定で変更でき、翌日以降も引き継ぐ。
- 当日の稼働時間はその日だけ上書き可能。
- 当日上書きは翌日に通常稼働時間へ戻る。
- `estimated_minutes` はAI初期値を人間が修正可能。
- `estimated_minutes` 未設定タスクは容量計算から除外し、「見積未設定」と表示する。
- 稼働可能時間の100%を超えた時点で警告表示する。
- 超過時は表示のみ。COMESが自動でタスク削減・移動・委譲提案はしない。

Google Calendar等との連携がないMVPでは、入力負荷を増やさず通常稼働時間を基準にする。将来Calendar連携時に固定予定時間を自動差し引ける構造へ拡張可能とする。

## 4. チーム画面

チーム画面は人事評価画面ではなく、マネージャーがチーム内の偏り・変化・要フォロー対象を横比較するための画面とする。

### 4.1 PCの基本表示

PCではカード一覧ではなく「横長の行」で一覧表示する。

正式な基本列:

```text
メンバー | 役割 | タスク数（仕事量） | 直近1on1実施日 | KPI進捗 | 直近の変化
```

「直近の変化」には必要に応じて次のようなシグナルを表示する。

- 褒める候補あり
- 要フォロー
- 委譲候補あり
- 変化なし

重要:
- 「評価点」「モチベーション点」などの人物スコアは表示しない。
- 数字だけで人を良し悪し判断するUIにしない。
- 事実・変化・候補シグナルを中心にする。
- 要フォローや褒める候補は根拠を追えるようにする。

### 4.2 メンバー押下時

メンバー行を押した場合、別ページへ即遷移せず、Homeと同じCentered Modalを表示する。

### 4.3 個人詳細モーダル

上段は人物サマリー、下段は3カラムとする。

#### 上段サマリー

- 名前
- 役割
- 所属チーム
- タスク数
- 直近1on1実施日
- KPI進捗
- 直近の変化サマリー

#### 下段3カラム

左: タスク状況
- 今日
- 1週間以内
- 急ぎじゃない
- 期限切れ
- 現在の主要タスク

中央: 1on1要約
- 主な話題
- 本人の発言
- 次回確認

右: 最近の変化
- 観測事項
- 褒める候補 / 要フォロー内容
- 委譲候補

人物評価ではなく、「仕事の事実」「本人の認識」「マネジメント判断材料」を横並びで見る構造とする。

## 5. 判断パック画面

判断パックは、AIに渡す前の判断材料を人間が確認・補正する画面である。

将来COMES内でLLM APIを実装した後も、AI入力の監査・説明・デバッグのためDecision Pack自体は残す。

### 5.1 基本タブ

判断パック画面は以下の2タブを持つ。

1. 判断材料
2. AI提案

### 5.2 判断材料タブ上部

上部に以下を表示する。

- 日付
- ステータス
- 最終更新
- `確認済みにする`
- `AI用プロンプトを作成`

ステータスは次の4段階:

1. 作成中
2. 確認済み
3. AI投入済み
4. AI結果取込済み

ステータス遷移:
- `確認済みにする` 押下時点をrevisionとして固定する。
- 確認済み後に判断パックを編集した場合は `作成中` に戻す。
- AI用プロンプトをコピーした時点で `AI投入済み` にする。
- 外部AIのJSONを貼り付け、Schema validationに成功した時点で `AI結果取込済み` にする。

### 5.3 判断材料の3カラム

PCでは以下を必須3カラムとして一画面で俯瞰する。

#### 左: 業務・KPI
- KPI進捗
- 異常・変化
- 停滞・ボトルネック

#### 中央: 人・チーム
- 要フォロー
- 褒める候補
- 委譲候補

#### 右: マネージャー・改善
- 自分の負荷
- 仕組み化候補
- AIに判断してほしいこと

各カードの通常表示は以下に留める。
- 件数
- 重要上位2〜3件
- 最優先ラベル

詳細・編集はCentered Modalで行う。

### 5.4 判断パック編集ルール

元データに由来する事実は編集不可とする。

人間が可能な操作:
- 追加
- 除外
- 補足
- 優先度変更

原則:
- 元の事実は固定。
- 自動生成版と人間編集版はrevisionを分ける。
- 誰が・いつ・何を変えたかはaudit logで追跡する。
- `decision_pack_note` は人間が追加した補足だけを示す。
- 優先度変更・除外などの編集履歴はsource_refsではなくrevision / audit logで管理する。

### 5.5 AI用プロンプト

個人MVPではLLM APIを使わず、固定テンプレート + 編集済みDecision Packの差し込みでAI用プロンプトを作成する。

フロー:

```text
Decision Pack確認・補正
→ AI用プロンプトを作成
→ プロンプト本文を必要に応じて手動編集
→ コピー
→ 外部AIへ投入
```

プロンプト欄は常時表示せず、`AI用プロンプトを作成` 押下後に画面下部またはModalで展開する。

プロンプト本文は手動編集可能とする。

## 6. AI提案タブ

AI提案タブは、外部AIから返された固定JSONをCOMESへ取り込み、人間が採否判断し、翌日のタスクへ接続する画面である。

### 6.1 AI結果取り込み

個人MVPではJSON専用の貼り付け欄を用意する。

取り込みフロー:

```text
外部AI
→ 固定JSON出力
→ COMES「AI結果を取り込む」へ貼り付け
→ JSON Schema validation
→ 成功時のみ保存
```

LLMによる自然文解析・JSON補正は行わない。

検証失敗時:
- 保存しない
- JSON構文エラー、必須項目不足、未定義enum、形式不正などをその場で表示する
- COMES側で推測補正しない

正式Schemaは B-24 `AI Analysis Result Schema v0.1` を参照する。

### 6.2 PC 3カラム

AI提案タブもCOMES全体のデザイン統一のため3カラムを採用する。

#### 左: 最優先・今日やること
- priority_task
- 今日実行すべき重要アクション

#### 中央: 人に関する提案
- follow_up
- praise
- one_on_one
- delegate

#### 右: 改善・構造
- bottleneck
- systemization
- 保留中の提案

委譲は「誰に任せるか」という人の文脈を優先し、中央に置く。

### 6.3 提案カードの状態

各提案カードに以下を持つ。

- 採用
- 保留
- 見送り

挙動:
- 採用: 確認モーダルなしで即タスク化
- 保留: AI提案タブに残す
- 見送り: 通常画面から外し、履歴へ退避

見送り提案は日常的に表示しないが、必要なときだけ履歴から確認できる。

AI提案履歴は日付ごとの提案セット単位で確認できる。

### 6.4 AI提案と翌日タスクの接続

理想の日次サイクル:

```text
当日を締める
→ Decision Pack生成
→ 人間が補正
→ AI用プロンプトをコピー
→ 外部AIで分析
→ 固定JSONをCOMESへ取り込み
→ 人間が採用 / 保留 / 見送り
→ 採用分だけ翌日のタスクへ即反映
→ 翌朝、タスク整理済みの状態から開始
```

COMESは「今日を締める」と「明日を作る」の間をつなぐManagement OSとする。

## 7. AIを脳みそとする責務境界

個人MVPではAI実行だけを外部AIに置く。

```text
COMES Core
→ Decision Pack
→ 外部AI
→ 固定JSON
→ COMES
→ 翌日タスク
```

将来LLM API実装後:

```text
COMES Core
→ Decision Pack
→ AI Analysis Adapter
→ LLM API
→ 固定JSON
→ COMES
→ 翌日タスク
```

外部AI利用は一時的なハーネスであり、COMESのCore仕様を外部AI依存にしない。

## 8. PC / Mobile

PC:
- Home上段カードは4列
- Home下段ブロックは3列
- タスク画面は3つの時間軸を横並び
- チーム画面は横長行による比較一覧
- 個人詳細はCentered Modal + 3カラム
- 判断材料は3カラム
- AI提案も3カラム

Mobile:
- PCを単純縮小しない
- Home上段カードは重要度順に縦配置、または横スワイプ候補
- Home下段は縦順
- 詳細表示は画面幅を大きく使うModal / Sheet候補
- タスクは「今日 → 1週間以内 → 急ぎじゃない」の縦順を基本候補
- チーム一覧は重要情報を縦カード化する方向
- 判断材料 / AI提案の3カラムはMobileでは縦順へ再配置する
- 最終的なMobile順序・表現は別途確定する

## 9. 未確定事項

以下は追加確認後に確定する。

- Home上段4カードの正式カテゴリ
- 各Homeカード内に表示する情報量
- Home Modal内のカテゴリ別アクション
- 確認事項リストの生成元
- 今日のスケジュールのデータソース
- チーム状態の定義と表示項目
- タスクの各グループ内ソート順
- タスクの手動追加 / 外部連携タスクの扱い
- 仕組み化候補の具体的な閾値
- チーム一覧の並び順・強調ルール
- AI提案カードの細部デザイン
- 判断材料カードの細部デザイン
- Mobileでの最終情報順序・Interaction Pattern

## 10. 現時点の原則

- UIは「管理帳票」ではなく「明日の行動を決めるManagement OS」として設計する。
- 人物スコアやモチベーション推定は行わない。
- 事実とAI提案、人間の補足を混同しない。
- 一覧は俯瞰性、詳細はCentered Modalで担保する。
- 操作回数を増やしすぎない。
- AI提案の採用後に再入力を要求しない。
- 個人MVPはLLM APIなしで成立させる。
- 将来LLM APIを内蔵しても、Decision Pack → AI Result → Taskという責務境界を維持する。
