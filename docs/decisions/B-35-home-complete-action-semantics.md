# B-35 HOME「完了」操作の種別別意味契約

Status: Accepted
Decision ID: B-35

## 結論

HOME上段4カードでは表示上のクイック操作文言を `完了` に統一してよいが、内部動作はカード種別ごとに意味を分ける。

COMESは異なるドメイン状態を単一のタスク完了状態へ潰さない。

## 種別別の意味

### 自分が動く

`完了` = 対象タスクを完了扱いにする。

- 対象が `work_items` の場合、`status = completed` へ遷移する。
- 完了日時等の既存監査情報を保持する。

### 手放す

`完了` = 委譲対応済み。

- 対象の委譲候補を「対応済み」として扱う。
- 元タスク自体を自動で `completed` にしない。
- 委譲先・委譲レベル・必要な次アクションが別途存在する場合、それらの業務状態を勝手に完了へ変更しない。

### 褒める

`完了` = 称賛・承認アクション実施済み。

- 対象人物や元業務の状態は変更しない。
- 「褒める候補を処理した」というマネジメント行動の完了として記録する。

### 詰まりを取る

`完了` = ボトルネック対応済み / 解消済み。

- ボトルネック候補は解消状態へ遷移可能。
- 元タスクや案件を自動で `completed` にしない。
- 実際に詰まりが解消していない場合は `完了` にしない。

## UI原則

表示上は操作数を増やさないため、HOMEでは共通ラベル `完了` を使用できる。

ただし詳細表示や操作後フィードバックでは、必要に応じて実際の意味を補足する。

例:
- タスクを完了しました
- 委譲対応済みにしました
- 称賛実施済みにしました
- ボトルネックを解消済みにしました

## 禁止事項

- 4カードすべてを `work_items.status = completed` へ変換する
- 候補処理完了を元業務完了と混同する
- `褒める` の完了で人物評価やスコアを更新する
- `手放す` の完了で委譲が実際に成立したと推測する
- `詰まりを取る` の完了で根拠なく案件完了扱いにする

## Acceptance

- HOMEの操作ラベルは簡潔なまま維持できる
- 4カードの異なるドメイン意味を保持できる
- タスク状態と候補処理状態を混同しない
- 完了操作による不要な副作用を防げる
